<task type="auto">
  <name>Task 1: Create /doc-writer:review audit skill</name>
  <files>skills/review/SKILL.md</files>
  <action>
Create the review skill that audits existing documentation without generating new content. Follow the existing skill pattern from `skills/setup/SKILL.md`.

Frontmatter:
```yaml
---
name: review
description: Audit existing documentation without generating new content. Runs Editor quality checks, Persona validation, and gap detection.
disable-model-invocation: true
allowed-tools: Agent, Read, Write, Glob, Grep, Bash
---
```

Skill body sections:

1. **Pre-Flight**: Read `.doc-writer/config.yaml`. If missing, tell user to run `/doc-writer:setup` first and stop. Verify docs exist in `paths.docs_root`. If no docs found, tell user to run `/doc-writer:write` first or point to existing docs directory. Extract audiences, detected.language, paths.

2. **Step 1: Gap Detection**: Read `detected.language` and `paths.source_root` from config. Run: `bash ${CLAUDE_PLUGIN_ROOT}/skills/write/scripts/scan-exports.sh {paths.source_root} {detected.language}`. Read existing docs to identify which symbols are documented. Write gap report to `.doc-writer/gap-report.md`.

3. **Step 2: Editor Audit**: Spawn doc-editor agent with delegation message: "Review the documentation in {docs_root}. Run all three passes: terminology consistency, humanizer review, cross-reference verification. Focus on identifying issues. Write your report to .doc-writer/editor-report.md." The Editor edits docs directly per its design (Phase 3 decision), so note that the Editor WILL make improvements as it audits. This is expected behavior -- the Editor's review IS its editing.

4. **Step 3: Persona Evaluation**: For each audience in config.audiences, spawn doc-persona agent with the audience name. Each produces an independent report.

5. **Step 4: Present Results**: Read editor-report.md and all persona-report files. Present a combined audit summary to the project author:
   - Gap detection results (undocumented exported symbols)
   - Editor findings by severity (BLOCKING, SUGGESTION, NITPICK) with counts
   - Persona verdicts per scenario per audience
   - Overall assessment

   Note: No revision loop. No PARTIAL approval flow. This is purely informational.
   Suggest: "Run `/doc-writer:edit` to fix specific issues, or `/doc-writer:write` for a full regeneration."

Important constraints:
- Do NOT use `context: fork`
- Do NOT commit any changes
- Do NOT run a revision loop -- this is audit-only
- The Editor WILL edit docs as part of its review (this is its design from Phase 3). The review command's value is the reports + Persona evaluation on top of Editor improvements.

Target 120-180 lines.

<task type="auto">
  <name>Task 2: Create /doc-writer:edit targeted fix skill</name>
  <files>skills/edit/SKILL.md</files>
  <action>
Create the edit skill that presents existing report issues for selection and applies targeted fixes. Follow the existing skill pattern.

Frontmatter:
```yaml
---
name: edit
description: Make targeted fixes to documentation based on report issues or freeform instructions.
disable-model-invocation: true
allowed-tools: Agent, Read, Write, Glob, Grep
argument-hint: "[issue description or page path]"
---
```

Note: No Bash in allowed-tools (edit does not run gap detection).

Skill body sections:

1. **Pre-Flight**: Read `.doc-writer/config.yaml`. If missing, tell user to run `/doc-writer:setup` first and stop.

2. **Step 1: Collect Available Issues**:
   - Read `.doc-writer/editor-report.md` if it exists
   - Read `.doc-writer/persona-report.md` and/or `.doc-writer/persona-report-{audience-name}.md` files if they exist
   - If NO report files exist: Present message: "No editor or persona reports found. Run `/doc-writer:review` first to generate an issues report, or describe your changes below." Skip to freeform-only mode.
   - If reports exist: Parse issues and present as a numbered list grouped by source:

   ```
   ## Available Issues from Previous Reports

   ### From Editor Report
   1. [BLOCKING] {page} > "{section}"
      {description}
   2. [SUGGESTION] {page} > "{section}"
      {description}

   ### From Persona Report ({audience})
   3. [FAIL] {page}
      {scenario_goal} -- {gap_description}
   4. [PARTIAL] {page}
      {scenario_goal} -- {friction_description}

   ### Custom
   N. Describe something else: ___

   Select issues to fix (e.g., "1,3" or "all" or just type a description):
   ```

   - If `$ARGUMENTS` is provided and is NOT a number selection, use it as the freeform instruction and skip the selection prompt. This allows direct invocation like `/doc-writer:edit fix the installation steps on getting-started.md`.

3. **Step 2: Author Targeted Revision**: Spawn doc-author agent with delegation message listing the specific selected issues with their full details (page, section, description, suggested fix from report). Instruct Author to: read config, revise ONLY the listed pages, do NOT regenerate other pages, focus on the specific issues described.

4. **Step 3: Editor Quality Pass**: Spawn doc-editor agent with delegation message: "Edit the revised pages: {changed_pages_list}. Run all three passes (terminology, humanizer, cross-references) on changed pages. Run the full terminology scan across ALL doc files (terminology changes can ripple)."

5. **Step 4: Done**: Present what was changed (list of modified pages and what was fixed per page). Note that docs are uncommitted -- project author should review diff and commit. Suggest: "Run `/doc-writer:review` if you want full validation of the changes."

Important constraints:
- Do NOT run Persona after edit (per locked decision)
- Do NOT commit changes
- Do NOT use `context: fork`
- Handle the "no reports exist" gracefully -- freeform always works
- If $ARGUMENTS is provided as text, treat it as the freeform instruction

Target 120-180 lines.

**Section 1: ## Admonitions**
Rules for RST admonitions (mapping from mkdocs-material.md Admonitions section):
- Prefer admonition directives over bold text for callouts. Directives create visual hierarchy.
- Use specific types instead of generic `.. note::`:
  - `.. tip::` for best practices and recommended approaches
  - `.. warning::` for gotchas, common mistakes, surprising behavior
  - `.. danger::` for breaking changes, security concerns, data loss risks
  - `.. note::` for supplementary context
  - `.. versionadded:: X.Y` for new features (Sphinx-specific, not in mkdocs-material)
  - `.. deprecated:: X.Y` for deprecation notices (Sphinx-specific)
- Do not stack multiple admonitions back-to-back. Consolidate into one with a list.
- Include short RST example showing `.. tip::` with indented body.

**Section 2: ## Code Blocks**
Rules for RST code blocks (mapping from mkdocs-material.md Code Blocks):
- Always use `.. code-block:: {language}` -- never use bare `::` for code that readers copy.
- Use `:emphasize-lines:` to highlight important lines. Do not highlight everything.
- Use `:caption:` to label file paths: `.. code-block:: python` with `:caption: src/main.py`.
- Use `:linenos:` only for long examples where line numbers aid discussion.
- Prefer tab sets (sphinx-design) over consecutive code blocks when showing same concept in multiple languages.

**Section 3: ## Tab Sets**
(New name -- maps to mkdocs-material's "Content Tabs"):
- Use `.. tab-set::` with `.. tab-item::` directives from sphinx-design for multi-language or multi-method examples.
- Use `:sync-group:` on the tab-set and `:sync:` on tab-items to synchronize related tabs across the page (e.g., all Python/JS tabs switch together).
- Keep tab labels short: "Python", "JavaScript", "pip", "conda" -- not "Python Example" or "Install via pip".
- Group related alternatives: install methods, OS-specific instructions, sync/async patterns.
- Do not use tabs for unrelated content. Different concepts get separate sections, not tabs.
- Include RST example:
```rst
.. tab-set::
   :sync-group: lang

   .. tab-item:: Python
      :sync: python

      .. code-block:: python

         client = MyClient(api_key="...")

   .. tab-item:: JavaScript
      :sync: js

      .. code-block:: javascript

         const client = new MyClient({ apiKey: "..." });
```

**Section 4: ## sphinx-design Components**
(New section -- no mkdocs-material equivalent. Per CONTEXT.md: cover all four groups with curated use-case guidance):

- **Grids + cards** (`.. grid::`, `.. grid-item-card::`): Use for landing pages, feature overviews, and section index pages. Grid responsiveness values `1 2 3 3` adapt from 1 column on mobile to 3 on desktop. Use `:link:` on cards for navigation.
- **Dropdowns** (`.. dropdown::`): Use for optional/advanced content that most readers can skip. Equivalent to collapsible admonitions in mkdocs-material. Use `:color:` and `:icon:` for visual distinction.
- **Badges** (`:bdg-success:`, `:bdg-warning:`, `:bdg-info:`): Use inline for version markers (`v2.1`), stability status (`stable`, `beta`), deprecation notices.
- **Buttons** (`.. button-ref::`): Use on landing pages for prominent calls-to-action (e.g., "Get Started" pointing to quickstart tutorial).
- Be pro-active about suggesting sphinx-design features where they improve clarity or navigation. Do not wait for the user to ask -- suggest grids for landing pages, tabs for multi-language code, dropdowns for advanced content.
- Reference link: full component inventory at https://sphinx-design.readthedocs.io/en/latest/

**Section 5: ## Navigation**

### Top-level tabs
- Use explicit `nav_links` in `html_theme_options` for top navbar tabs. Shibuya does NOT automatically derive tabs from the toctree (unlike mkdocs-material). The `nav_links` must be configured in conf.py pointing to each Diataxis section index page.
- Standard tab set: Home (root index.rst), Tutorials, How-To Guides, Explanation, Reference.
- Disable tabs for simple projects where all sections have only 1-2 pages each. At that scale, a single sidebar works better.
- Tabs are a separate nav layer above the left sidebar. With tabs configured, the sidebar shows contents of the section the reader is currently viewing.

### Left nav depth
- Keep left nav to 3 levels maximum (section heading -> page -> sub-page). Deeper nesting creates narrow, scrolling nav panels.
- Level 1: section heading (e.g., "Authentication"). Level 2: page (e.g., "OAuth Setup"). Level 3: sub-page as child entry.
- Use `index.rst` files for section landing pages with a toctree listing the section's pages.
- Root `index.rst` should use a hidden toctree (`:hidden:`) listing all Diataxis section indexes so the sidebar populates without rendering a visible list.

**Section 6: ## Page Metadata**
(Maps to mkdocs-material "Frontmatter" -- RST does not use YAML frontmatter):
- RST pages do not use YAML frontmatter. Use field lists at the top of a page for metadata, or `:orphan:` to exclude from toctree warnings.
- Use page titles (RST heading underlines) as the canonical title. Do not duplicate in metadata.
- For tutorials, include difficulty context in the opening paragraph rather than metadata fields.

**Section 7: ## Cross-References**
(Per CONTEXT.md locked decisions -- this is critical):
- Use `:ref:\`label\`` for ALL internal links. Place labels (`.. _label-name:`) above headings. Labels survive page moves; `:doc:` references break on restructure.
- STRONGLY DISCOURAGE `:doc:\`path\`` for internal navigation. It couples links to file paths. Use `:ref:` with descriptive labels instead.
- Use intersphinx roles for external Sphinx project links: `:py:class:\`pathlib.Path\``, `:py:func:\`os.path.join\``. These resolve via intersphinx_mapping.
- Inline code mentions of project APIs should use `:py:func:\`my_func\``, `:py:class:\`MyClass\`` -- which link to autoapi-generated pages automatically.

**Section 8: ## sphinx-autoapi Integration**
(New section -- no mkdocs-material equivalent):
- autoapi output REPLACES the Reference tab entirely. The Author agent MUST NOT write manual reference pages when autoapi is enabled.
- Google docstring style is the convention. All docstrings should follow Google style (Parameters, Returns, Raises, Example sections).
- Place autoapi output under `reference/api/` using `autoapi_root = "reference/api"` in conf.py.
- Set `autoapi_add_toctree_entry = False` and manually include `api/index` in `reference/index.rst` toctree. This prevents autoapi from injecting at the root toctree level.
- Set `autoapi_python_class_content = "both"` to show both class-level and `__init__` docstrings.

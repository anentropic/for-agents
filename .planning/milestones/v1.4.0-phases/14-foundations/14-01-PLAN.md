## Mermaid Diagrams

MkDocs Material renders mermaid diagrams natively through the pymdownx.superfences custom fence already configured in the scaffold. No additional plugins or configuration needed.

- Use standard fenced code blocks with the `mermaid` language identifier:

  ````markdown
  ```mermaid
  sequenceDiagram
      participant User
      participant API
      User->>API: POST /items
      API-->>User: 201 Created
  ```
  ````

- Mermaid diagrams render in both light and dark mode automatically via Material's built-in theme integration.
- Do NOT add `mkdocs-mermaid2-plugin` -- it is redundant with the pymdownx.superfences custom fence and can cause conflicts.
- Diagram source is written inline in the Markdown file. No external files or build steps required.
```

**sphinx-shibuya.md** -- append this section:

```markdown
## Mermaid Diagrams

Sphinx renders mermaid diagrams via the `sphinxcontrib-mermaid` extension (already included in the scaffold conf.py). The extension must be installed: `pip install sphinxcontrib-mermaid`.

- Use the `.. mermaid::` RST directive. The diagram source is indented under the directive:

  ```rst
  .. mermaid::

     sequenceDiagram
        participant User
        participant API
        User->>API: POST /items
        API-->>User: 201 Created
  ```

- Shibuya theme handles dark/light mode diagram rendering automatically.
- The scaffold sets `mermaid_version = ""` which uses the bundled version from sphinxcontrib-mermaid. Do not override this unless a specific mermaid.js version is required.
- Do NOT use fenced code blocks (` ```mermaid `) in RST files -- Sphinx does not recognize them. Always use the `.. mermaid::` directive.
```

**odoc.md** -- append this section:

```markdown
## Mermaid Diagrams

odoc has no native mermaid rendering support. Use a workaround: include the mermaid source as a verbatim block for reference, and link to an externally-generated SVG for the rendered diagram.

- Include mermaid source in a `{v ... v}` verbatim block so readers can see the diagram definition:

  ```ocaml
  (** Architecture overview.

      The processing pipeline follows this flow:

      {{:./diagrams/pipeline.svg} Pipeline diagram}

      Mermaid source for reference:

      {v
      flowchart LR
          A[Input] --> B{Validate}
          B -->|Valid| C[Process]
          B -->|Invalid| D[Error]
          C --> E[Output]
      v}
  *)
  ```

- To generate the SVG, use the mermaid CLI (`mmdc`) outside of odoc: `mmdc -i pipeline.mmd -o diagrams/pipeline.svg`. Store `.mmd` source files alongside the generated SVGs.
- Do NOT use or recommend `odoc-mermaid` or any experimental odoc mermaid extension -- these are not on opam stable and are not production-ready.
- The `{v ... v}` block renders as preformatted text, not as a diagram. The SVG link provides the visual rendering.
```

**plain-markdown.md** -- append this section:

## Mermaid Diagrams

GitHub renders mermaid diagrams natively in Markdown files, Issues, PRs, and wikis. Other Markdown renderers may not support mermaid.

- Use standard fenced code blocks with the `mermaid` language identifier:

  ````markdown
  ```mermaid
  flowchart LR
      A[Input] --> B{Validate}
      B -->|Valid| C[Process]
      B -->|Invalid| D[Error]
      C --> E[Output]
  ```
  ````

- Mermaid blocks render as diagrams on GitHub. On renderers without mermaid support, they appear as syntax-highlighted code blocks -- still readable, just not visual.
- Keep diagrams simple. Complex diagrams with many nodes may not render well in narrow views (mobile, GitHub PR diffs).
```

Insert the following section:

```markdown
### Mermaid Diagram Awareness

When writing explanation pages, how-to guides with multi-step processes, or any content that describes flows, states, or relationships, consider whether a mermaid diagram would help the reader understand the concept faster than prose alone.

**Diagram type selection:**

| Content Area | Diagram Type | When to Use |
|-------------|-------------|-------------|
| API request/response flows, multi-step interactions | `sequenceDiagram` | Shows temporal ordering of messages between participants |
| Decision trees, process flows, pipelines | `flowchart` (or `graph TD`/`graph LR`) | Shows branching logic and directional flow |
| Lifecycle states, state machines, status transitions | `stateDiagram-v2` | Shows states and transitions between them |
| Type hierarchies, module relationships, data models | `classDiagram` | Shows structural relationships and inheritance |

**Rules:**
- Read the mermaid syntax from the doc-system guidance file (`.doc-writer/{doc_system}.md`). Do NOT hardcode mermaid wrapper syntax -- each framework uses a different format.
- Use diagrams to supplement prose, not replace it. A diagram without surrounding explanation is as unhelpful as a code block without context.
- Place diagrams near the concept they illustrate -- after the introductory paragraph, before the detailed breakdown.
- Keep diagrams focused: 3-8 nodes for flowcharts, 2-4 participants for sequence diagrams. Busy diagrams confuse more than they clarify.
- Not every page needs a diagram. Use them for concepts that involve flow, state, or structure. Straightforward API usage docs rarely benefit from diagrams.
```

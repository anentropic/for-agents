**Part A: Gap detection script** (`skills/write/scripts/scan-exports.sh`)

Create a bash script that scans source code for exported symbols. The script takes two arguments: `source_root` and `language`. It outputs exported symbols grouped by category, one per line in `file:line:symbol` format.

Language support:
- `python`: Scan for `__all__` definitions, public functions (`^def [^_]`), public classes (`^class [^_]`), public constants (`^[A-Z][A-Z_]*\s*=`)
- `typescript` / `javascript`: Scan for `^export ` in `.ts`, `.tsx`, `.js`, `.jsx`, `.mts`, `.mjs` files
- `rust`: Scan for `^pub ` in `.rs` files
- `go`: Scan for `^func [A-Z]`, `^type [A-Z]`, `^var [A-Z]`, `^const [A-Z]` in `.go` files
- Unknown languages: Print a message that Claude will scan manually

Exclude directories: `node_modules`, `.venv`, `venv`, `__pycache__`, `.git`, `dist`, `build`, `test`, `tests`, `spec`, `target`.

Use the exact script structure from 05-RESEARCH.md "Gap Detection Script" section. Make it executable.

**Part B: /doc-writer:write skill** (`skills/write/SKILL.md`)

Create the full pipeline orchestration skill. Follow the existing skill pattern from `skills/setup/SKILL.md`.

Frontmatter:
```yaml
---
name: write
description: Generate new documentation using the full Author > Editor > Persona pipeline with gap detection, revision loop, and quality validation.
disable-model-invocation: true
allowed-tools: Agent, Read, Write, Glob, Grep, Bash
argument-hint: "[--skip-gap-scan]"
---
```

Skill body sections (step-by-step orchestration instructions Claude follows):

1. **Pre-Flight**: Read `.doc-writer/config.yaml`. If missing, tell user to run `/doc-writer:setup` first and stop. Extract `audiences` (array), `doc_system`, `paths.source_root`, `paths.docs_root`, `detected.language`. Note audience count for Persona spawning.

2. **Step 1: Gap Detection** (skip if `$ARGUMENTS` contains `--skip-gap-scan`):
   - Read `detected.language` and `paths.source_root` from config
   - Run: `bash ${CLAUDE_PLUGIN_ROOT}/skills/write/scripts/scan-exports.sh {paths.source_root} {detected.language}`
   - Read existing docs in `paths.docs_root` to identify which exported symbols already have documentation
   - Write gap report to `.doc-writer/gap-report.md` listing each undocumented exported symbol grouped by module/file with total count
   - If previous gap-report.md exists, note which gaps are newly discovered vs persistent

3. **Step 2: Author**: Spawn doc-author agent with delegation message instructing it to generate docs, read config, and read gap-report.md for undocumented symbols to prioritize. On revision passes, provide targeted page list and instruct to read persona-report for specific gaps.

4. **Step 3: Editor**: Spawn doc-editor agent to run all three passes (terminology, humanizer, cross-references) on the authored docs.

5. **Step 4: Persona Evaluation**: For each audience in config.audiences, spawn a doc-persona agent with the audience name. If multiple audiences, note they produce independent reports (`persona-report-{audience-name}.md`).

6. **Step 5: Verdict Check and Revision Routing** (state machine):
   - Read all persona reports and collect verdicts per scenario
   - All PASS across all audiences -> go to Step 6 (PARTIAL approval) or Step 7 (summary)
   - Any FAIL and pass_count < 3 -> increment pass_count, extract FAIL gaps (pages + what's missing), go to Step 2 (Author revision with targeted pages), then Step 3 (Editor on changed pages + full terminology), then Step 4 (Persona with reused scenarios)
   - Any FAIL and pass_count >= 3 -> ESCALATION: present remaining FAILs to project author with context of what was tried across passes, recommend manual intervention
   - Only PARTIAL (no FAIL) -> go to Step 6

7. **Step 6: PARTIAL Approval** (batch at end):
   - Collect all PARTIAL fix suggestions from all persona reports
   - Present as numbered list showing: audience, scenario ID, page, section, issue description, suggested fix
   - Ask project author to respond with numbers (e.g., "1,3"), "all", or "none"
   - Apply approved fixes directly to doc files (Claude writes changes). Do NOT re-run pipeline for PARTIAL fixes.
   - Include a freeform option: "Or describe additional changes:"

8. **Step 7: Summary Report**: Present completion summary showing: pages written/revised (list), Editor changes applied (count and types), Persona verdicts per scenario per audience, revision passes taken (count), remaining PARTIALs (if any rejected), gap detection results (undocumented symbols found). Note that docs are uncommitted -- project author should review diff and commit when satisfied.

Important constraints to encode in the skill:
- Do NOT use `context: fork` (per research -- loses user interaction for PARTIAL approval)
- Do NOT commit generated docs (per locked decision)
- Do NOT regenerate Persona scenarios on revision passes (reuse existing from scenarios.yaml)
- Revision loop: only FAILs trigger revision, max 3 total passes (initial + 2 revisions)
- Multi-audience: separate Persona per audience, aggregate verdicts across ALL audiences before routing
- If `.planning/PROJECT.md` exists, mention it as optional context for Author (light touch, not a dependency)

Target 300-400 lines for the skill. Use clear markdown section headers. Keep delegation messages concise.

**Title and intro:**

```markdown
# Doc Writer Upgrade

Upgrade the doc-writer configuration after the plugin has been updated. Detects version changes, migrates config fields, updates unchanged files, and reports all changes in a summary.
```

**User Interaction Pattern block:** Copy the exact block from setup SKILL.md (lines 13-19). Same text, same formatting. This is needed because the upgrade skill uses AskUserQuestion for ambiguous config field inference (D-05, D-06).

**Instructions section:** Must contain "Follow these steps in order. Read each section carefully before acting." then implement these 4 steps:

**Step 1: Version Detection**

Instructions for Claude to:
1. Read `.doc-writer/config.yaml`. If it does not exist, inform user: "No doc-writer configuration found. Run `/doc-writer:setup` first." Stop.
2. Extract `plugin_version` from config.yaml. If `plugin_version` field is absent, treat as `"unknown"` (pre-1.5.0 project). Display: "Config has no plugin_version field -- treating as pre-1.5.0 project."
3. Read `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`. Extract the `version` field. (IMPORTANT: this is the `version` field in plugin.json, not `plugin_version`.)
4. If `plugin_version` equals the plugin.json `version`: display "doc-writer is already up to date (version {version})." Stop. (per UPGRADE-01, D-03)
5. Display: "Upgrading doc-writer from {old_version} to {new_version}..."
6. Store both versions for use in Step 4 summary.

CRITICAL (Pitfall 6): Do NOT write the new plugin_version to config.yaml in this step. It must be written LAST in Step 4, after all migration is complete.

**Step 2: Config Format Migration**

Instructions for Claude to:
1. Read `${CLAUDE_PLUGIN_ROOT}/skills/setup/defaults/config-template.yaml` as the canonical schema.
2. Compare user's config.yaml fields against the template fields.
3. **Exclude from comparison** these meta-fields (managed by setup/upgrade, not user fields): `version`, `plugin_version`, `detected`, `qa_answers`. Explicitly list these exclusions in the SKILL.md text so Claude knows not to treat them as migration targets.
4. **Identify new fields** -- fields present in config-template.yaml but absent from user's config.yaml (after excluding meta-fields). For each new field:
   - Examine the user's existing config values holistically to infer an appropriate value. The inference should feel natural -- as if the user had been asked the question during setup and answered based on their existing configuration. (per D-04)
   - Inference rules by field type:
     - String field: infer from other config fields with related semantics
     - Array field: infer from related arrays or decomposition of existing string fields
     - Boolean field: infer from existing config state (e.g., `use_cases_section: false` if `use_cases` is empty or has only blank entries)
     - Nested object: infer from existing flat fields or reasonable project-context defaults
   - If inference is clear and unambiguous: write the value silently. Record for summary: "Added {field}: {value} (inferred from {source})". (per D-04)
   - If inference is ambiguous (more than one plausible interpretation): use AskUserQuestion with the field's valid values as labeled options. Include a "Type something else" option and a "Chat about this" option. (per D-05, D-06)
   - NEVER copy placeholder/empty values from config-template.yaml. Every new field must have a real, inferred value. (Pitfall 2)
5. **Identify deprecated fields** -- fields present in user's config.yaml but absent from config-template.yaml (after excluding meta-fields). Auto-remove without prompting. Record for summary: "Removed deprecated field: {field}". (per D-08, D-09)
6. If no new fields AND no deprecated fields detected: record "No config schema changes" for summary. Do not write config.yaml unnecessarily. (Pitfall 7)
7. If changes were made: write the updated config.yaml with new fields added and deprecated fields removed. Preserve all existing user values for unchanged fields. Maintain YAML formatting.

**Step 3: Unchanged File Update**

Instructions for Claude to:
1. Check if `.doc-writer/.originals/` directory exists (use Glob for `.doc-writer/.originals/*`).
   - If directory does not exist or is empty: display "This project was set up before upgrade support was available. File comparison skipped. Run `/doc-writer:setup --reset` to establish baseline files." Record this warning for summary. Skip to Step 4.
2. Read the `doc_system` value from the user's config.yaml (needed to identify the guidance file name).
3. For each file in `.originals/` (typically `rules.md` and `{doc_system}.md`):
   a. Read `.doc-writer/.originals/{file}` -- this is BASE (the previous plugin default).
   b. Read `.doc-writer/{file}` -- this is USER (the user's current copy).
   c. Determine the corresponding new plugin default path: `${CLAUDE_PLUGIN_ROOT}/skills/setup/defaults/{file}`. Check if this file exists. If it does not exist (FALLBACK framework -- the guidance file was researcher-generated, not shipped by the plugin): skip this file. Record for summary: "Skipped {file} -- not a plugin-shipped file."
   d. Read the new plugin default -- this is NEW.
   e. If BASE content is identical to NEW content: no upstream changes to this file. Skip. (Nothing to report.)
   f. If USER content is identical to BASE content: user has not customized this file. Silently overwrite `.doc-writer/{file}` with NEW content. ALSO update `.doc-writer/.originals/{file}` with the same NEW content (Pitfall 5 -- must update .originals/ to avoid future false "customized" detection). Record for summary: "Updated {file} to new plugin version." (per D-10)
   g. If USER content differs from BASE content: user has customized this file. Do NOT modify it. Record for summary: "Skipped {file} -- file has been customized. Merge support coming in a future upgrade." (per D-11)

**Step 4: Finalize**

Instructions for Claude to:
1. Write the new `plugin_version` value (the version from plugin.json) to `config.yaml`, replacing the old value. This is the LAST write to config.yaml. (Pitfall 6)
2. Display a consolidated upgrade summary with clear sections:

```
## Upgrade Summary

**Version:** {old_version} -> {new_version}

### Config Changes
- {list each added field with inferred value and source}
- {list each removed deprecated field}
- {or "No config schema changes"}

### File Updates
- {list each file updated (unchanged files overwritten)}
- {list each file skipped (customized, deferred to merge)}
- {list each file skipped (FALLBACK/not plugin-shipped)}
- {or "No file updates" / ".originals/ not found -- skipped"}

### Warnings
- {any warnings from above steps}
- {or "None"}
```

(per D-07 -- consolidated summary of every field added and removed. Exact wording is Claude's discretion.)

**End of instructions.** The skill must NOT contain placeholder steps for Phase 20 (3-way merge) or Phase 21 (Q&A gap detection). The command delivers a minimal complete slice and stops after Step 4. (per D-03)

**Total expected file size:** ~200-300 lines of markdown (comparable to other skills, smaller than setup's 591 lines since the flow is simpler).

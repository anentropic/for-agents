**Section 3: Full Q&A Flow** (first-time setup) — Must cover:

b) **Doc system selection**: Present detected doc system (from auto-detection) as default. Options: mkdocs-material, plain-markdown, or custom (user enters name). If custom, note that the user should create `.doc-writer/{name}.md` guidance file.

  <action>
Create the three default files that get copied to `.doc-writer/` during setup:

1. **`skills/setup/defaults/mkdocs-material.md`** — MkDocs Material guidance file. This is NOT a syntax reference (agents already understand MkDocs syntax). This is opinionated preferences for feature usage. Sections:

   - **Admonitions**: Prefer admonition blocks over bold text for callouts. Use `!!! tip` for best practices, `!!! warning` for gotchas, `!!! danger` for breaking changes. Use collapsible `??? note` for optional/advanced details. Prefer specific types over generic `!!! note`.
   - **Code Blocks**: Always specify language. Use line highlighting (`hl_lines`) for important lines. Use code annotations for complex examples. Prefer tab-separated multi-language examples over separate code blocks.
   - **Tabs**: Use content tabs for same concept in multiple languages. Short tab labels ("Python", not "Python Example Code"). Group related alternatives (install methods, OS-specific instructions).
   - **Navigation**: Max 3 levels deep. Group related pages. Use index pages for sections.
   - **Frontmatter**: Every page needs `title` and `description`. Tutorials get `difficulty` level.
   - **Cross-References**: Use `[text][reference]` style for internal links. Inline code mentions link to API reference.

   ~40-60 lines. Each preference should include a brief "why" or "instead of X, do Y" rationale.

2. **`skills/setup/defaults/plain-markdown.md`** — Plain markdown guidance file. For projects without a specific doc system. Sections:

   - **Structure**: Use ATX headings (`#`), not setext. Max heading depth: 4 levels.
   - **Code Blocks**: Always fenced (triple backtick), always specify language. No indented code blocks.
   - **Links**: Prefer reference-style links `[text][ref]` for repeated URLs. Inline `[text](url)` for one-off links.
   - **Emphasis**: Bold for UI elements and important terms on first use. Italic for book/document titles. Inline code for function names, parameters, file paths, CLI commands.
   - **Lists**: Use `-` for unordered (not `*` or `+`). Use `1.` for ordered (not `1)` or other markers). Indent nested lists with 2 spaces.
   - **Tables**: Use for structured data (parameters, options, comparisons). Align columns. Keep tables under 5 columns.
   - **Callouts**: Use blockquotes with bold labels: `> **Note:** ...`, `> **Warning:** ...` since no admonition syntax is available.

   ~30-40 lines. Simpler than mkdocs-material since fewer features to opine on.

3. **`skills/setup/defaults/rules.md`** — Default project-specific rules file. This is the file that gets copied to `.doc-writer/rules.md` in the user's project. It is freeform markdown that agents interpret. Per user decision, these rules are ADDITIVE to universal rules (they extend, not override).

   Content:
   ```markdown
   # Project Documentation Rules

   These rules are specific to this project and extend the universal quality rules
   enforced by all doc-writer agents. Edit this file to add project-specific
   documentation guidelines.

   ## How Rules Work

   - Universal rules (no internal details, working examples, consistent structure,
     cross-references, audience calibration) are always enforced and cannot be
     overridden.
   - Rules in this file are additive — they add project-specific requirements on
     top of the universal baseline.
   - Write rules as natural language instructions. Agents interpret them directly.

   ## Project Rules

   <!-- Add your project-specific documentation rules below. Examples: -->

   <!-- - Always include a "Requirements" section in how-to guides listing minimum versions -->
   <!-- - Use American English spelling throughout -->
   <!-- - Code examples must show error handling, not just the happy path -->
   <!-- - Reference the changelog entry when documenting breaking changes -->
   ```

   The file should be ~20-30 lines, mostly instructional with commented-out examples. The user edits this file for their project.

**Per user decisions:**

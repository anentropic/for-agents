### Unsatisfied Requirements (1)

#### P11-03: sphinx-shibuya conf.py scaffold

**Status:** partial
**Assigned:** Phase 11 (11-01-PLAN.md)
**Root cause:** Static content verification passed (the scaffold file exists with correct Shibuya configuration), but runtime integration check reveals a template variable mismatch:

- `scaffolds/sphinx-shibuya.py` uses: `{project_name}`, `{author_name}`, `{copyright_year}`, `{github_url}`
- `setup/SKILL.md` Step 2b.3 substitutes only: `{site_name}`, `{site_description}`

**Result:** When a user selects sphinx-shibuya in a project with no `conf.py`, the generated `conf.py` will contain literal placeholder strings (`project = "{project_name}"`, `author = "{author_name}"`, etc.) rather than real values. The Sphinx build metadata will be incorrect.

**Fix:** Either (a) rename template variables in `sphinx-shibuya.py` to match what SKILL.md substitutes, and prompt for the remaining fields, or (b) extend `setup/SKILL.md` Step 2b.3 to also infer and substitute `{project_name}`, `{author_name}`, `{copyright_year}`, `{github_url}`.

## Integration Findings

### MISSING-01: doc-researcher WebFetch missing from tools frontmatter

**File:** `doc-writer/agents/doc-researcher.md` line 4
**Affected:** P10-03, P10-06, P10-07

The Unknown Framework Research mode (line 212) instructs the agent to "Use WebFetch to find the framework's official documentation." WebFetch is not in the `tools:` frontmatter. Claude Code will refuse WebFetch calls; the agent always falls back to LOW confidence (training knowledge only).

**Impact:** Tech debt (degraded quality, not broken flow — LOW confidence output is still produced and functional).

---

### MISSING-02: doc-researcher Framework Preferences limited to mkdocs-material/plain-markdown

**File:** `doc-writer/agents/doc-researcher.md` line 118
**Affected:** P11-06

The `## Framework Preferences` block in context.md is only generated when `doc_system is mkdocs-material or plain-markdown`. sphinx-shibuya and odoc projects receive no framework-specific enrichment in context.md. Downstream agents still read the guidance files directly, so formatting preferences are not entirely absent — but the richer "Features to Use / Features NOT to Use" expansion based on actual project config won't be produced.

**Impact:** Tech debt (guidance files still work; context.md framework preferences are a quality enhancement, not a blocker).

---

**File:** `doc-writer/skills/setup/defaults/scaffolds/sphinx-shibuya.py` lines 8-10, 50
**Affected:** P11-03

See "Unsatisfied Requirements" section above. This is the only critical gap blocking milestone completion.

### MISSING-04: OCaml/odoc support gaps in doc-author and scan-exports.sh

**Files:** `doc-writer/agents/doc-author.md`, `doc-writer/skills/write/scripts/scan-exports.sh`
**Affected:** AUTH-04 (partially)

`scan-exports.sh` has no OCaml case — the `*)` catch-all produces an unstructured gap report for OCaml projects. `doc-author.md` has no conditional logic for OCaml-specific file types (`.mld` guide pages, `.mli` doc comments) or for the odoc author scope (which the user selected in Q2 of odoc.qa.md).

**Impact:** Tech debt. The odoc guidance file (`odoc.md`) is correctly read by the author, providing formatting preferences. But the author will write output to `paths.docs_root` as `.md` files rather than `doc/` as `.mld` files. AUTH-04 is otherwise well-wired for all other doc systems; this is an odoc-specific limitation.
